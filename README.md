# UsageWatch

Windows 前台应用使用时长记录器。只做一件事：**在你没锁屏、没走开的时候，记下前台是哪个窗口，然后把时间花在哪了摊开给你看。**

没有云端、没有账号、没有遥测，数据全部留在本机的一个目录里。

```
┌────────────────────────────────────────────────────────────────┐
│ 11月17日 周二                    9:00 ──────────────── 18:43   │
│                                                                │
│ 7h 12m                                    活跃跨度 10.0h       │
│ ▲ 1h 11m 高于近 30 天中位 6h 01m                                │
│                                                                │
├──────────────────────────────┬─────────────────────────────────┤
│ 时间去向                     │ 主要去处                        │
│ 编码      ███████ 42%        │ Cursor          2h 53m  40%      │
│ 沟通      ████    24%        │ 知乎            55m     13%     │
│ 资讯社区  ██      13%        │ 云之家          39m      9%     │
│ 业务系统  █       7%         │ 微信            21m      5%     │
└──────────────────────────────┴─────────────────────────────────┘
```

## 特点

- **单进程**：托盘常驻 + 内嵌 HTTP 服务，双击就跑，不依赖 IIS、Node、数据库。
- **极小**：`HttpListener` 手写路由，发布后 `exe + dll` 共约 300 KB，不是几十兆的 Web 框架。
- **三层归类**：分类 → 站点/项目 → 页面/文件。能回答「时间是花在写代码，还是花在知乎」，而不只是「Edge 占了 34%」。
- **带参照系**：主数字旁边直接给「高于/低于近 30 天中位」，不用自己跟历史比。
- **归类可外置**：规则写在 `%APPDATA%\AppUsage\rules.json`，看板右上角「规则」进配置页可视化维护，保存即生效，不用重启也不用重新编译。
- **崩溃不丢数据**：30 秒心跳写 `state.json`，进程被强杀后重启会把这半段补偿回来。

## 快速开始

要求：Windows 10/11 + [.NET 10 Desktop Runtime](https://dotnet.microsoft.com/download/dotnet/10.0)。

```bash
git clone https://github.com/Fine974/UsageWatch.git
cd UsageWatch
dotnet build -c Release
dotnet run -c Release
```

或者自己发布一份免 SDK 的绿色版：

```bash
dotnet publish -c Release -o dist
./dist/usagewatch.exe
```

启动后双击托盘图标，或访问 `http://127.0.0.1:5279`（端口被占用时会自动换一个，实际端口写在 `%APPDATA%\AppUsage\port.txt`）。

想先看效果但没有数据，可以造一天假数据：

```bash
python make_demo.py            # 写入今天
python make_demo.py 2026-11-11 # 写入指定日期
```

## 命令

不带参数启动＝托盘模式（采集 + 看板）。

| 命令 | 作用 |
|---|---|
| `usagewatch.exe` | 托盘常驻：启动采集、内嵌看板、单例保护 |
| `run` | 前台运行采集，不开 Web。适合排查 |
| `serve` | 只起看板，不采集 |
| `status` | 采集状态、当前前台窗口、今日段数与心跳 |
| `report --date 2026-11-17` | 导出静态 HTML 日报，`--html <path>` 指定路径，`--no-open` 不自动打开 |
| `unknown --top 30` | 列出**没被任何规则命中**的页面，按累计时长排序 —— 用来知道该补什么规则 |
| `probe` | 打印当前前台窗口的进程名、标题、类名、空闲秒数、是否锁屏。写规则前先用它确认 |

采集参数：`--interval 5`（采样间隔秒）、`--idle 600`（空闲多少秒判定为离开）、`--no-title`（不记录窗口标题，只要时长）。

## 数据与隐私

所有数据在 `%APPDATA%\AppUsage\`：

| 文件 | 内容 |
|---|---|
| `2026-11-17.jsonl` | 当天的使用分段，一行一段 |
| `state.json` | 心跳，用于进程被强杀后补偿最后一段 |
| `port.txt` | 看板实际监听端口 |
| `rules.json` | 你的外置归类规则（可选） |

一行数据长这样：

```json
{"t":"2026-11-17T09:12:00","e":"2026-11-17T09:38:00","p":"chrome","w":"某页面标题","s":1560}
```

`t`/`e` 起止时间，`p` 进程名，`w` 窗口标题（`--no-title` 时为空），`s` 秒数。

**窗口标题会包含你在看什么**，这是它准确归类的代价。不想记录就加 `--no-title`，代价是所有站点归并成一个进程名，看板上看不到具体页面。数据不上传任何地方，仓库也 `.gitignore` 了 `*.jsonl`。

## 归类规则

### 三层结构

```
进程 msedge + 标题「deepseek 深度求索 - 知乎 - Microsoft Edge」
   └─ 分类：资讯社区        ← 决定柱状图颜色、是否算工作
      └─ 站点：知乎         ← 决定「去处分布」
         └─ 页面：deepseek 深度求索
```

标题先做归一化才能得到稳定结果。浏览器会在标题里塞标签页数量、私信未读数、应用名，不剥掉的话同一个页面会被拆成几十条（实测知乎被拆成 34 个不同标题，真实的 Top1 在排行里根本看不见）。

### 匹配优先级

**顺序很重要，踩过的坑：**

1. `sites` 规则按数组顺序匹配，**先命中先用**，所以更具体的必须排在更笼统的前面（「Swagger」要排在「开放平台 / API文档」这类宽泛规则之前）。
2. **站点规则优先于 apps 规则**。如果某进程的窗口标题恰好命中了站点规则，apps 里为它配的 group 会被忽略 —— 这时要改站点规则，不是改 apps。
3. **站点规则不分进程**。别写太宽的模式，比如裸的 `orders` 会把 IDE 里同名项目的窗口也吃掉。
4. **同名站点必须同分类**，否则站点层聚合会取到先出现的那个分类，数字会串。

内置规则只收录通用软件与公开网站。公司内部系统、内网地址这类个性化规则请写进 `rules.json` —— 它优先级更高，可以覆盖内置，也不会把内部信息带进代码仓库。格式见 [`rules.example.json`](rules.example.json)。

### 没归类怎么办

跑 `usagewatch.exe unknown`，它按累计时长列出所有规则没覆盖到的页面：

```
     累计    进程  页面
------------------------------------------------------------------------------
   1h 04m   msedge  内部 Wiki
     6m     msedge  General
```

看到值得补的就往 `rules.json` 里加一条。浏览器兜底分类是 **`未归类`** 而不是「资讯社区」—— 未命中就默认算娱乐，会系统性地低估工作占比，把规则缺口藏起来。

### 配置页

看板右上角「规则」，或直接开 `http://127.0.0.1:5279/rules`。

「还没被规则覆盖的」把两类缺口分开列：网页没命中站点规则的归 **未归类**，进程没配应用规则的归 **其他** —— 两者要用不同手段解决，混在一起看容易写错规则。每条右边点「归类」，正则已经按标题预填好（编号、日期这类易变内容剥掉了，否则规则过两天就失效），改完可以就地试跑，确认能命中再加入。

保存做三件事：旧文件备份到 `rules.json.bak`、原子写入、重建规则表并清掉归类缓存。所以保存即生效，**历史数据也会跟着重算** —— 补一条规则，上周的记录当场就归到正确分类去，不用等新数据。

规则顺序就是生效顺序，列表里的 ↑↓ 可以调。写正则之前建议先用页面底部的「规则试跑」验一遍：最容易踩的坑是「以为命中了其实没命中」，或者被更靠前的宽泛规则先吃掉，试跑会直接告诉你是谁命中的、在内置还是外置。

## 看板

- **主数字 + 基线**：今天总时长，下面直接给与近 30 个工作日中位的差值，再往下是 30 天趋势柱，当前日高亮。
- **时间去向**：分类占比条，每条上的竖线是历史中位位置，一眼看出哪类今天偏多。
- **值得注意**：只挑和平时不一样的 —— 分类偏离 ≥8 个点、最长专注 <8 分钟、未归类 ≥5 分钟、覆盖率低于中位 12 个点、切换超过中位 1.4 倍。都正常时退回展示专注、离开、碎片化这类行为观察。
- **折叠区**：每小时堆叠柱、站点甘特图，需要看时间定位时再展开。
- **亮/暗主题**：默认亮色，右上角切换，记在 `localStorage`。

静态日报（`report`）复用同一份模板与渲染脚本，可以直接发给别人看。

## 已知限制

- **只有 Windows**。核心依赖 `GetForegroundWindow` / `GetLastInputInfo`。
- **归类靠窗口标题**，不读进程内存、不读浏览器历史。IDE 类应用按标题里的项目名归类，所以 Cursor 的 Agents 面板这种固定标题的界面，归不到具体项目。
- **空闲判定是启发式的**。`--idle 600` 意味着 10 分钟没有键鼠操作就判定离开，看长文档或开会时这段会被漏记。这是覆盖率通常只有 70%–75% 的主要原因。
- **不做周/月视图**（暂无），不做多机同步。
